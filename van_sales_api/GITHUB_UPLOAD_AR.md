# إصلاح الاتصال وبدء التشغيل — التطبيق والسيرفر 0.8.2 / API 8

## نتيجة المراجعة

التطبيق 0.8.0 وإضافة السيرفر 0.8.1 يعلنان API 8. إصدار السيرفر 0.8.1 السابق غيّر التوثيق والتجهيز فقط. رقم الإصدار وحده لا يثبت أن الموقع نشر الملفات الصحيحة أو نفّذ الترحيل.

عُثر على عيب في بدء التشغيل: فشل bootstrap بسبب نشر ناقص أو خطأ سيرفر/صلاحيات يوقف الوصول إلى الواجهة، ويمنع الاستفادة من الكاش. وكان فحص الأعمدة يرمي خطأ عامًا قبل إتمام التهيئة. هذه مشكلات مؤكدة من الكود. سبب رسالة جهازك تحديدًا لم يُؤكد لأن نص الرسالة وسجل الموقع لم يُقدما، ولم تتوفر صلاحية قراءة المستودع الحالي أو الدخول إلى موقعك.

## ما تغير

- استعادة الجلسة تحتفظ بالحساب والكاش عند أخطاء السيرفر، وتعرض شاشة استرداد بدل ترك التطبيق عند خطأ التهيئة. فشل المصادقة الحقيقي أو اختلاف المستخدم يعيد تسجيل الدخول.
- الجلسة الجديدة التي نجح دخولها وفشل bootstrap تتحقق من هوية المستخدم عبر مسار Frappe المستقل get_logged_user قبل حفظ الجلسة. كلمة المرور لا تُحفظ.
- فشل التوافق لا يستبدل كاشًا صالحًا بتهيئة جزئية فارغة. عرض الكاش يحتاج حساب الجلسة نفسه وبيانات سابقة مهيأة. تبقى الطلبات المحلية بمعرفاتها.
- يوجد زر «فحص الاتصال» في الرئيسية وفي شاشة الاسترداد. يوضح إصدار الإضافة وAPI والحقول والملفات الناقصة. تقرير النسخ يستبعد كلمات المرور وsid وCSRF وهوية المستخدم.
- مسار الفحص van_sales_api.connection.status مستقل عن استيراد واجهات العمليات المالية، ويحتاج جلسة مصادقة.
- bootstrap على السيرفر غير المكتمل يعيد حالة إعداد غير جاهزة بدل قراءة بيانات الأعمال. الحفظ والاعتماد وتحديث المسودات موقوفة على السيرفر عند عدم اكتمال البنية. التطبيق أيضًا يمنع POST عند اكتشاف فشل التوافق؛ نجاح bootstrap كامل يعيد فتح الإرسال.
- لم تتغير سياسة الخصم أو تسعير العميل أو الطباعة أو الباركود أو تشفير SQLite.

## ترتيب تثبيت الإصلاح

1. احتفظ بنسخة احتياطية من الموقع وسجّل آخر نشر ناجح. احتفظ أيضًا بأي مسودات محلية؛ لا تزل تطبيق الهاتف ولا تمسح بياناته.
2. ثبّت VanSalesAndroid-0.8.2.apk فوق التطبيق الحالي مباشرة. معرّف التطبيق ومفتاح التوقيع محفوظان، ورقم النسخة الداخلي ارتفع إلى 9. هذا الإصلاح يُفضّل تثبيت APK أولًا حتى يعالج تهيئة السيرفر الجزئية ويحافظ على الكاش.
3. فك van_sales_api-FrappeCloud.zip وافتح مجلد van_sales_api الخارجي. ارفع محتوياته إلى جذر المستودع المستخدم فعليًا في Frappe Cloud، بما فيها المجلدات الداخلية كاملة. يجب أن يكون pyproject.toml في جذر المستودع وبجواره مجلد van_sales_api.
4. ارفع إلى الفرع الذي تستخدمه الاستضافة فعلًا. اكتب Commit واضحًا مثل Update van_sales_api 0.8.2 API8 connection recovery.
5. تأكد على GitHub أن van_sales_api/__init__.py يحتوي __version__ = "0.8.2" وAPI_VERSION = 8، وأن van_sales_api/connection.py موجود.
6. تحقق أيضًا من وجود المسار van_sales_api/van_sales_api/doctype/mobile_sales_settings/mobile_sales_settings.json. تكرار اسم van_sales_api في المسار الداخلي صحيح.
7. من Frappe Cloud حدّث بناء البيئة وانشر آخر Commit، ثم حدّث الموقع ونفّذ الترحيل Migrate. انتظر نجاح سجل العملية بالكامل. رفع GitHub وحده لا يحدّث الموقع. حافظ على اسم الإضافة van_sales_api ولا تحذفها أو تُعد تثبيتها باسم مختلف.
8. افتح التطبيق واضغط «فحص الاتصال والتوافق». يجب ظهور إضافة 0.8.2 وAPI 8 و«جاهزة» دون عناصر ناقصة.
9. عد إلى شاشة الاسترداد واضغط «إعادة المحاولة»، ثم نفّذ المزامنة. فتح الفحص وحده لا يرسل المسودات ولا يمسحها. راجع المسودات ثم اعتمد المطلوب صراحةً.

## رفع الملفات من واجهة GitHub

- افتح المستودع والفرع الصحيحين، ثم Add file → Upload files.
- اسحب محتويات مجلد الإضافة المستخرج، بما فيها المجلدات، إلى صفحة الرفع. لا ترفع ملف ZIP كبديل للكود، ولا تضف مجلد الإصدار الخارجي فوق جذر المشروع.
- راجع أن المسارات تبدأ pyproject.toml وvan_sales_api/api.py وvan_sales_api/connection.py. الملفات ذات المسار نفسه تُحدّث؛ رفع ملفات الجذر وحدها يترك DocTypes ناقصة.
- Commit changes، أو افتح Pull Request وادمجه وفق حماية مستودعك، ثم انشر Commit نفسه من لوحة الاستضافة.

## قراءة تقرير الفحص

- API أقل من 8: الموقع يشغّل إضافة قديمة. تحقق من المستودع والفرع وCommit الذي نُشر فعلًا.
- Missing files: أعد رفع الملفات المذكورة والمجلدات كاملة، ثم أعد البناء والنشر.
- Missing schema: اكتمل جزء من الكود، وتحتاج قاعدة الموقع إلى Migrate. راجع سجل فشل الترحيل إن استمرت العناصر.
- Schema inspection unavailable: تعذر فحص بعض جداول الموقع؛ راجع سجل السيرفر وقاعدة البيانات والترحيل.
- HTTP 401 أو خطأ Authentication: أعد تسجيل الدخول بعد التأكد من صلاحية المستخدم والجلسة.
- HTTP 403: راجع نوع الخطأ المعروض وصلاحيات المستخدم. لا تُمنح صلاحيات مسؤول للمندوب كحل عام.
- HTTP 404/417/500 أو عدم وجود مسار الفحص: تحقق من وصول connection.py إلى بيئة الموقع، وتثبيت الإضافة، وصحة رابط الموقع وسجل النشر. إذا غاب مجلد الإضافة بالكامل فلن يتمكن أي مسار منها من العمل.
- الفحص جاهز لكن ما زال bootstrap يعرض خطأ: انسخ تقرير الفحص وأرسل صورة رسالة الاسترداد. يلزم سجل الخطأ على الموقع لتحديد خطأ الصلاحيات أو التخصيصات الفعلي.

يمكن للمسؤول المسجل في ERPNext فتح /api/method/van_sales_api.connection.status على عنوان الموقع نفسه لفحص الإضافة مباشرة. لا ترسل ملفات Cookies أو كلمات مرور أو مفاتيح API أو CSRF عند مشاركة نتيجة الفحص.
